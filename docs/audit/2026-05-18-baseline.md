## C. PROBLEM DEFINITION

**Quoted from README.md:2:**
> "TriageIQ turns raw GitHub issues into structured triage decisions in under 4 seconds. Given an issue title and body, it runs a four-stage ML pipeline — component classification, duplicate retrieval, resolution-time prediction, and LLM synthesis — and returns a JSON `TriagePlan` with predicted component, similar issues, expected resolution window, priority assessment, and suggested next steps. It is trained on ~20K real issues from `microsoft/vscode` and `kubernetes/kubernetes`, deployed to Cloud Run, and built to demonstrate a full production ML lifecycle: evaluation, reproducible builds, Prometheus metrics, fail-closed auth, Workload Identity Federation CI/CD, and CVE-audited dependencies."

**Concrete scope confirmed in code:**
- `schemas.py:TriageRequest.repo` — `Literal["microsoft/vscode", "kubernetes/kubernetes"]` — exactly two repos in production.
- Data card (`reports/01_data_card.md:14`) — tensorflow, pytorch, airflow also scraped but **not** in production serving path.

**Labels / targets:**

| Task | Type | Classes / Output |
|---|---|---|
| System 1: Component | Multi-class classification | 28 classes (vscode), 35 classes (kubernetes) |
| System 2: Duplicate | Dense retrieval / nearest-neighbor | Top-k similar issues (k=5 default) |
| System 3: Resolution time | Regression with quantile bands | log1p(hours) → days, Q10/Q90 intervals |
| System 4: Priority | LLM-generated Literal | `"low"` / `"medium"` / `"high"` |
| System 4: Triage plan | Generative JSON | TriagePlan schema (10 fields) |

## E. MODELING APPROACH

**Systems in production (all inferred from `src/triage_iq/models/` and `loader.py`):**

**System 1 — TF-IDF + Logistic Regression** (`component_classifier.py`)
- `TfidfVectorizer(max_features=50_000, ngram_range=(1,2))` → `LogisticRegression(class_weight="balanced", solver="saga", C=1.0, seed=42)`
- Repo-specific models (separate label vocabularies).
- Results (`reports/classifier_results.json`):

| Repo | Train n | Test n | Classes | Accuracy | Macro-F1 | p50 latency |
|---|---|---|---|---|---|---|
| vscode | 1,488 | 187 | 28 | 69.0% | 0.585 | 4.9ms |
| kubernetes | 2,284 | 286 | 35 | 51.4% | 0.466 | 5.6ms |

- Worst classes by F1: vscode — `editor-core (0.0)`, `electron (0.0)`, `search (0.0)`, `workbench-editors (0.0)`, `suggest (0.08)`. kubernetes — `cloudprovider (0.0)`, `etcd (0.0)`, `extensibility (0.0)`, `isolation (0.0)`.
- ECE calibration: 0.496 (vscode), 0.396 (kubernetes) — poor probability calibration; mean confidence is 0.19 vs mean accuracy 0.69. The confidence scores passed to the LLM prompt are systematically low.

**System 2 — BGE-base-en-v1.5 + FAISS** (`duplicates.py`)
- `sentence-transformers BAAI/bge-base-en-v1.5`, `IndexFlatIP` (cosine, L2-normalized), CPU-only.
- Results (`reports/duplicate_results.json`):

| Repo | Model | Pairs | MRR | Recall@5 | Recall@10 | p50 latency |
|---|---|---|---|---|---|---|
| vscode | BGE | 411 | 0.294 | 36.7% | 52.1% | 26.7ms |
| vscode | MiniLM | 411 | 0.267 | 35.3% | 50.6% | 24.0ms |
| kubernetes | BGE | 1,024 | 0.316 | 41.0% | 47.4% | 39.5ms |
| kubernetes | MiniLM | 1,024 | 0.266 | 35.6% | 43.5% | 23.3ms |

- BGE chosen for production (higher MRR). MiniLM indices present but unused.
- Index sizes: vscode BGE 24.3 MB, kubernetes BGE 50.1 MB.

**System 3 — LightGBM quantile regression** (`resolution.py`)
- 93 engineered features: text length, temporal, label presence, component one-hot (top-10), author history (leak-proof), cross features, BGE → PCA-64 embeddings.
- Three models per repo: point (MAE loss), Q10, Q90. Target: `log1p(resolution_hours)`.
- Results (`reports/resolution_results.json`):

| Repo | Train n | Test MAE | vs Naive | CI coverage | Top feature |
|---|---|---|---|---|---|
| vscode | 4,923 | 3.4 days | +19.1% | 42.5% | `has_type` |
| kubernetes | 11,974 | **682 days** | +3.3% | **0.0%** | `has_priority` |

- **Kubernetes predictor is practically useless.** Naive baseline MAE = 705 days; model improves by 3.3% to 682 days. Confidence intervals cover 0% of held-out examples. Root cause: kubernetes dataset is Jun 2014 – Oct 2015 only, bimodal resolution with no temporal signal generalizable to test period.

**System 4 — Groq llama-3.1-8b-instant** (`triage.py`, `prompts/triage_prompt.py`)
- 3-shot JSON generation. System prompt + 3 few-shot pairs + user turn with all System 1–3 signals.
- Retry on JSON parse failure (1 retry with stricter prompt). Fallback to TF-IDF component + medium priority if both fail. `triage.py:~280`
- Groq resilience: 6 attempts, exponential backoff, handles RateLimitError + APIStatusError ≥ 500. `triage.py:~250`
- Results (`reports/triage_results.json`, n=60 gold issues):

| Metric | Value |
|---|---|
| Judge score (Full System) | 10.93/15 (73%) |
| Judge score (TF-IDF only) | 4.55/15 (30%) |
| Judge score (TF-IDF + BGE) | 8.48/15 (57%) |
| LLM component accuracy | 58.3% |
| TF-IDF component accuracy | 61.7% |
| Majority baseline | 11.7% |
| Best judge dimension | similar_issues_relevance (2.72/3) |
| Worst judge dimension | resolution_estimate_reasonableness (1.28/3) |

- **LLM does not improve over TF-IDF on component accuracy (58.3% vs 61.7%).** The LLM adds value in next_steps and priority_rationale, not classification.

**Tried and abandoned:**
- `scripts/05_train_distilbert.py` — DistilBERT fine-tuning. Checkpoints present in `data/models/distilbert_component_*/`. Decision documented in `65d106d: "honest analysis on DistilBERT vs TF-IDF at small data scale"`. Not in production.
- `scripts/06_eval_llm_fewshot.py` — LLM few-shot baseline standalone evaluation. Not in production serving.

**Current best model artifacts:**
- `data/models/component_classifier_microsoft_vscode.pkl` — TF-IDF + LR
- `data/models/dup_index_microsoft_vscode_bge/` — FAISS index
- `data/models/resolution_predictor_microsoft_vscode.pkl` — LightGBM

## L. INFERENCE

GG is building a portfolio-grade ML system demonstrating end-to-end production ML: multi-system pipeline (classical ML + dense retrieval + gradient boosting + LLM), evaluated rigorously via LLM-as-judge, deployed to Cloud Run with proper CI/CD, observability, and auth. The project is ~85% complete by scope: the vscode path is solid and production-ready; the kubernetes path is a partial citizen with a broken resolution predictor (MAE 682 days, +3.3% over naive) and lower classifier accuracy. The biggest risk to model quality is the data, not the models: vscode's 28.1% component fill means the classifier is trained on a 28% coverage subset of a bimodal distribution spanning incompatible labeling eras (2015-16 team labels vs 2025-26 community labels). The classifier achieves 69% accuracy on its own test set but that test set is sampled from the same bimodal pool — it likely performs considerably worse on fresh 2025+ issues where `triage-needed` and `agents` labels dominate. The fix is label re-extraction: update the vscode allowlist for modern label conventions, or replace the allowlist with regex-based extraction matching the kubernetes pattern, then re-scrape specifically for labeled 2020-2026 issues to close the coverage gap.

## M. MONOREPO vs SPLIT RECOMMENDATION

**Keep split.** The evidence supports it: different runtimes (Python 3.11 FastAPI vs Node/Vite), different CI/CD systems (GitHub Actions → GCP vs Vercel native), different release cadences (backend has 45 commits and an active deploy pipeline; UI was built in 3 days of polish commits after the backend was production-stable), and different scaling concerns (backend needs memory-bound model loading, UI is static). The cost of merging — retooling both CI systems, adding monorepo orchestration (Turborepo/nx), re-linking Vercel — would exceed the benefit at current scale for a solo project. The one real problem is type drift: `TriagePlan` and `SimilarIssue` are duplicated across Python and TypeScript with no code-generation contract. This should be solved without merging: generate TypeScript types from the FastAPI OpenAPI spec via `openapi-typescript` as a pre-commit or CI step in the UI repo, then delete the hand-written interfaces in `App.tsx:58-80`.
